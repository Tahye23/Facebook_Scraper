1. Vue d’ensemble

Système de scraping multi-plateforme (Facebook + TikTok) orienté métadonnées de posts + analyse IA Gemini, exposé via une API Gateway Spring Boot, orchestré par RabbitMQ, persisté dans MongoDB, packagé entièrement en Docker Compose.

Objectif TikTok : scraper un profil ou un CSV, streamer vite les résultats à l’utilisateur, enrichir ensuite avec Gemini, et gérer le re-scrape sans historique inutile.

MessagingRabbitMQ
PersistenceMongoDB

3. Décisions d’architecture (pourquoi)

Gateway + workers (pas monolithe)ADR

Contexte

Le scrape Playwright est long, fragile, CPU/RAM lourd.

Décision

API Spring séparée des workers Python.

Pourquoi

API responsive ; scale workers indépendamment ; isolation des crashes browser.

Conséquences

Évolutions résultats = souvent gateway + worker.

Alternatives rejetées

Scrape synchrone dans l’API = timeouts HTTP et blocage.

RabbitMQ (pas HTTP synchrone worker)ADR

Contexte

Besoin de buffer, retry, multi-plateformes.

Décision

Exchange scrape.exchange + queues dédiées + result queue + DLQ.

Pourquoi

Découplage, résilience, plusieurs consumers possibles.

Conséquences

Observer les files (UI :15672) en debug.

Alternatives rejetées

Appels HTTP gateway→worker : couplage fort, pas de buffer.

Mongo 1 doc / (platform, postId)ADR

Contexte

Besoin de l’état actuel d’une vidéo, pas d’un journal.

Décision

Upsert unique ; scrapeId rattache au dernier job.

Pourquoi

Simplifie cache Gemini et GET results.

Conséquences

Pas de timeline metrics historique (sauf évolution future).

Alternatives rejetées

Historique complet = complexité et coût stockage.

Streaming métadonnées puis GeminiADR

Contexte

Gemini est lent/coûteux ; l’utilisateur veut voir tôt.

Décision

Publish RESULT immédiat, puis ENRICHMENT async.

Pourquoi

UX streaming + économie IA via cache video_report.

Conséquences

Deux messages Rabbit par post enrichi.

Alternatives rejetées

Attendre Gemini avant tout affichage = UX mauvaise.

Sticky proxy = sticky Chrome profileADR

Contexte

Cookie global sur IP aléatoires → soft-block TikTok (grille vide).

Décision

sdwopfmy-N → tiktok_sessions/sdwopfmy-N/ persistent context.

Pourquoi

Cookies/fingerprint nés sous la même IP sticky.

Conséquences

Volume Docker obligatoire pour survivre aux recreate.

Alternatives rejetées

Un seul profil Chrome partagé = détection / locks.

Pool 20k + sample + blacklistADR

Contexte

Beaucoup d’IP meurent (tunnel, auth, soft-block).

Décision

Sample N IP/job, blacklist ciblée, rotation fail-fast.

Pourquoi

Résilience sans dépendre d’une seule IP.

Conséquences

Surveiller proxy_blacklist.json pour éviter pool brûlé.

Alternatives rejetées

IP unique fixe = SPOF.

Chrome headed + XvfbADR

Contexte

Headless pur plus souvent détecté.

Décision

TIKTOK_HEADLESS=false + DISPLAY=:99 sous Xvfb.

Pourquoi

Fingerprint plus proche d’un navigateur réel en Docker.

Conséquences

Image plus lourde ; besoin Xvfb dans le container.

Alternatives rejetées

Headless seul = plus de soft-blocks observés.

TTL metrics 12h + exception nullADR

Contexte

Re-scrape fréquent ne doit pas écraser metrics fraîches, ni bloquer un 1er scrape sans likes.

Décision

Si metrics présentes et <12h → garder ; si null → accepter incoming.

Pourquoi

Équilibre fraîcheur / coût scrape.

Conséquences

Bug historique corrigé : TTL bloquait likes même quand null.

Alternatives rejetées

Toujours écraser = charge inutile ; jamais écraser = metrics figées null.

Le gateway publie selon platform. Les workers publient RESULT / ENRICHMENT / COMPLETED / ERROR.

7. Streaming & Gemini

  1. Dès qu’une vidéo est trouvée → publish métadonnées + metrics (si dispo)
  2. Après scrape → pour chaque post : cache DB video_report ou appel Gemini sur la description texte
  3. Publish enrichment update → le client voit le report apparaître

Gemini est surtout text-only ici → confidence.level = low/medium est normal sans audio/visuel.

8. MongoDB — modèle & cache

ScrapeResult : 1 document par (platform, postId). Champs clés : author, textContent, hashtags, metrics, videoReport, publishedAt, scrapedAt, scrapeId.

Avant Gemini, le worker appelle l’API interne gateway pour récupérer les reports déjà connus et sauter l’analyse IA.

10. Pipeline scrape TikTok

  1. launch_persistent_context sur profil sticky
  2. Warmup homepage (+ auto-warm si session froide)
  3. Open profil + wait ancres /video/
  4. Extract DOM + SIGI/universal data + réseau (hors For You)
  5. Scroll jusqu’à max_posts / empty scrolls
  6. Enrich : ouvrir pages /video/ pour stats / statsV2 / DOM counts
  7. Return posts → worker stream + Gemini

Fail-fast : si aucune ancre /video/ après wait → soft-block → rotate (pas 2×25s inutiles).

11. Rapports métier

  • Par vidéo : video_report Gemini (thèmes, résumé, sentiment, keywords, confidence…)
  • Batch CSV : rapport agrégé Mauritanie 24h HTML + PDF (+ fallback si timeout Gemini)

12. Système de logs

Module logging_setup.py → JSON structuré : timestamp, level, logger, message, platform, service, scrape_id, url, post_id.

  • Soft proxy fail → WARNING (sans stack Playwright)
  • Bug inattendu → ERROR + traceback
  • Corréler via scrape_id

16. Pièges à ne pas casser

  1. Ne pas réinjecter cookies globaux sur IP aléatoires en mode sticky
  2. Ne pas lancer 2 Chrome sur le même tiktok_sessions/<id>/
  3. Ne pas traiter no_posts_found comme succès vide sans rotation
  4. Ne pas relancer Gemini si video_report existe
  5. Ne pas oublier le volume Docker des sessions
  6. Ne pas logger les passwords proxies
  7. Ne pas retirer l’exception TTL « metrics null »

17. Évolutions prioritaires

  1. Healthcheck proxy avant d’ouvrir Chrome
  2. Dashboard succès / blacklist / latence
  3. Mode metrics-only refresh sans Gemini

  5. Téléchargement média seulement si confidence basse
